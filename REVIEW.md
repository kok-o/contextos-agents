## 1. Главное обещание опровергается собственным продуктом

README, benefit №1:

> **Save Tokens & Context:** ContextOS dynamically loads only the required skills… This prevents context window bloat.

Что реально генерирует экспортёр:

| Файл | Размер | ~Токенов (4 симв./токен) |
|---|---|---|
| `.cursorrules` | 303 617 | ~76 000 |
| `CONVENTIONS.md` | 303 689 | ~76 000 |
| `.zed/rules.md` | 305 829 | ~76 500 |
| `.github/copilot-instructions.md` | 305 582 | ~76 400 |

Для Cursor, Copilot, Aider и Zed продукт — это один монолит на ~76k токенов, который грузится **в каждый запрос целиком**. Это не «экономия контекста», это худший из возможных вариантов.

Добивает вот что — строка 20 внутри самого `.cursorrules`:

> **Core law: Do not read everything. Read only what the current task requires.**

Этот закон написан внутри 76-тысячетокенного блоба, который читается целиком, всегда. Продукт лечит болезнь, которую сам же и вызывает у 4 из 6 поддерживаемых агентов.

## 3. «Benchmark», которого не существует

`.agents/core/skills/ponytail-mindset/SKILL.md:25`:

> **Benchmark**: 54% less code on average. 94% less in over-build scenarios. **100% safe**.

Слово «Benchmark» подразумевает измерение. В репозитории нет ни скрипта, ни датасета, ни методологии, ни сырых данных для этих чисел. «100% safe» — вообще не измеримое утверждение ни при какой методологии. То же самое с «saving up to 65% in active prompt tokens» в описании MCP.

Это не преувеличение — это выдуманные числа, поданные как результат измерения. Если кто-то технический это заметит (а заметит), доверие ко **всему** README обнулится, включая честные части.

## 4. «Dynamic Skill Resolution Engine» — это список регексов

`.agents/resolver.js` — 21 правило вида «слово → скилл». Нет скоринга, нет ранжирования, нет ограничения на количество. README обещает:

> dynamically resolves the **exact 2–4 skills** needed

В коде нет ни одного кэпа. Это `Set`, в который всё сваливается объединением. Проверено на живой фразе из обычных английских слов:

```
$ node .agents/ctx.js resolve "I need to update the user module and query
                               the index type of the container session token"

Skills loaded: ponytail-mindset, engineering-workflow, typescript,
               database, security, docker, nestjs, system-design
```

8 навыков:

- `docker` — потому что «container»
- `nestjs` — потому что «module»
- `database` — потому что «query» и «index»
- `typescript` — потому что триггер `/\btypes?\b/i` ловит слово «type»

Обещано 2–4, получено 8, и половина — мусор.

## 5. Тесты написаны так, чтобы не найти этот баг

`tests/resolver.test.js` — 8 тестов, все проверяют только `assert.ok(res.skills.includes(...))`. **Ни одного** `assert.ok(!res.skills.includes(...))`.

Единственный реальный режим отказа этой архитектуры — переcрабатывание — не покрыт by construction. Тесты подтверждают happy path и физически не способны поймать проблему из пункта 4.

В остальных 116 тестах есть и откровенно тавтологичные:

```js
test('"npm run validate" script is defined in package.json', ...)
```

Это тест того, что кто-то написал строчку в JSON. Он никогда не поймает баг. `116 tests, 0 fail` в README — цифра честная, но она меряет не то, что кажется.

## 7. Нет .gitattributes

Запущено ровно то, что написано в README:

```
$ node .agents/ctx.js export all
$ git status --porcelain | wc -l
194
```

194 файла «изменились». Проверено через `--ignore-all-space` — контент идентичен, дрейф чисто CRLF. Причина: `.gitattributes` в проекте нет.

То есть любой контрибьютор на Windows, выполнив документированную команду, немедленно получает 194-файловый мусорный дифф. Автор сам разрабатывает на Windows — значит либо спотыкается об это каждый раз, либо коммитит эти CRLF-флипы вперемешку с реальной работой.

## 8. CI не проверяет ту платформу, на которой ведётся разработка

Все джобы в `.github/workflows/validate-skills.yml` и `publish.yml` — `runs-on: ubuntu-latest`. Ни одной `windows-latest`.

При этом в коде есть Windows-специфика (`npm.cmd` в `plugins.js`), и в истории коммитов есть:

```
b9d9c59 fix(mcp): add retries to worktree cleanup to prevent EBUSY on Windows
```

Windows-баги в этом проекте — не гипотеза, они уже случались. И CI их по-прежнему не ловит.

Заодно: CI выполняет `export all`, но нигде не сверяет результат с закоммиченным. Дрейф «источник → generated» не отлавливается вообще.

## 9. Swarm молча мёртв на Windows

`contextos-mcp/src/agents/claude-code.ts:15` — и идентично в `aider.ts`, `codex.ts`, `opencode.ts`:

```ts
const proc = spawn("which", [cmd], { stdio: "pipe" });
proc.on("error", () => resolve(false));
```

```
$ grep -rn "win32\|process.platform" src/agents/
(пусто)
```

Ноль платформенных гардов. На Windows `which` не существует → срабатывает `error` → `commandExists` возвращает `false` → **ни один агент не детектится, и никакой ошибки не показывается**. Вся фича «autonomous multi-agent swarm» тихо не работает на платформе автора.

И это ровно тот раздел README, который называется:

> ### Enterprise Architecture Guarantees

Забавно, что в `plugins.js` гард `process.platform === 'win32' ? 'npm.cmd' : 'npm'` есть. Значит про эту категорию багов автор знает — просто в MCP-часть эти знания не доехали.

## Что сделано хорошо

Не всё плохо, и это стоит сказать прямо.

`.agents/plugins.js` — заметно выше среднего по индустрии:

- валидация сегментов пути с явным отсевом `.` и `..`
- пиннинг хоста при редиректе (`hostname !== 'raw.githubusercontent.com'` → отказ)
- `--ignore-scripts`
- установка в `mkdtemp` вне проекта
- запись sha256

Человек, который это писал, думал об атаках.

**Две дыры в нём же:**

- **sha256 записывается, но ни с чем не сверяется.** Это журнал, а не проверка целостности. Нет способа сказать «установи вот этот скилл и только если его хеш равен X».
- **Имя npm-пакета не валидируется вообще** — в отличие от GitHub-ссылки, которая проверяется тщательно. Пакет с именем на `-` уедет в `execFileSync` как флаг npm.

**И более крупная вещь, которую защита пропускает концептуально:** `SKILL.md` из произвольного GitHub-репозитория компилируется **прямо в системный промпт агента** без какой-либо проверки содержимого. Здесь контент и есть исполняемый код. `--ignore-scripts` защищает от npm-скриптов, но не от того, что в скачанном markdown написано «ignore previous instructions». Это классическая supply-chain prompt injection — в проекте, где есть скилл `security` с пунктом «Prompt Injection defense».

**Ещё плюсы:** тесты реально запускаются и проходят, структура адаптеров чистая, CI-пайплайн для публикации по тегу сделан аккуратно (валидация semver, `npm ci --ignore-scripts`), схема реестра есть.

## Диагноз

Реальная суть проекта: **хорошо организованная библиотека промпт-шаблонов с мульти-IDE экспортёром**. Это нормальный, полезный, честный продукт.

Проблема в том, что он одет в костюм «Context OS / Compiler / Engine / Enterprise Runtime / Autonomous Swarm», и костюм рассыпается от первой же проверки:


- Regex-словарь назван «Dynamic Resolution Engine»
- 76k-токенный блоб продаётся как экономия токенов
- Выдуманные проценты помечены как «Benchmark»
- Фича, мёртвая на Windows, называется «Enterprise Guarantees»

Число как аргумент — «39 skills», «23 roles», «50 rules», «405 tests» — встречается в README чаще, чем любое доказательство, что от них есть польза. Нигде не показано, что 39 навыков работают лучше пяти.

Технический человек, зайдя в репозиторий, за десять минут найдёт битые ссылки на бенчмарки и «100% safe» без методологии — и после этого не поверит уже ничему, включая те части, которые правдивы. Оверклейм здесь вредит не абстрактно, он съедает кредит доверия к реально хорошей работе (тот же `plugins.js`).

## Часть II: Аудит безопасности рантайма, MCP и готовности к релизу

> **Оценка release-readiness: 3/10, RED. Проект не готов к production и публичному релизу.**  
> Главная проблема: это не просто «есть баги». MCP-слой предоставляет агенту возможность выполнять произвольные команды, читать файлы вне проекта и разрушительно менять Git-репозитории без изоляции.

### P0 — Блокеры релиза

#### 1. Произвольное выполнение команд через `verify_command`
- **Локация:** [contextos.ts:45](file:///c:/Users/esenb/Desktop/my_geni/contextos-mcp/src/mcp/tools/contextos.ts#L45)
- **Суть:** `verify_command` приходит от непроверенного MCP-клиента и исполняется через системный шелл: `execAsync(command)`.
- **Риск:** Позволяет запускать произвольные бинарники, использовать цепочки операторов `&&`, `;`, `|`, синтаксис PowerShell/CMD и читать окружение процесса.
- **Утечка ключей:** В дочерний процесс прокидывается весь `process.env`, включая API-ключи провайдеров (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`).

#### 2. Отсутствие защиты директории проекта
- **Локация:** [contextos.ts:72](file:///c:/Users/esenb/Desktop/my_geni/contextos-mcp/src/mcp/tools/contextos.ts#L72)
- **Суть:** Параметр `dir` проверяется только через `existsSync`.
- **Отсутствующие проверки:**
  - путь является валидным Git-репозиторием (`.git` существует);
  - путь находится строго внутри разрешённого рабочего каталога (workspace whitelist);
  - путь указывает на директорию, а не на произвольный файл хоста;
  - путь не является симлинком на защищённые области системы;
  - клиент авторизован на работу с данным путём.

#### 3. Path Traversal в механике Worktree
- **Локация:** [manager.ts:111](file:///c:/Users/esenb/Desktop/my_geni/contextos-mcp/src/worktree/manager.ts#L111)
- **Суть:** `threadId` формируется из пользовательского `provider` без белого списка или безопасной санитизации.
- **Риск:** Конкатенация пути `path.join(this.baseDir, \`wt-${threadId}\`)` с `../` и слэшами приводит к выходу за пределы `baseDir`. Последующий вызов `rmSync(wtPath, { recursive: true, force: true })` способен уничтожить системные или пользовательские каталоги на хосте.

#### 4. Python Runtime — ложная иллюзия песочницы
- **Локация:** [runtime.py:252](file:///c:/Users/esenb/Desktop/my_geni/contextos-mcp/src/core/runtime.py#L252)
- **Суть:** Вызов `exec(compiled, _user_ns)` выполняется со стандартными `__builtins__`.
- **Риск:** Код имеет неограниченный доступ к модулям `os`, `sys`, `subprocess`, файловой системе, сокетам, сетевому стеку и переменным окружения. Заявление «isolated namespace» вводит разработчиков в заблуждение.

#### 5. Утечка секретов и чувствительных файлов в LLM
- **Локация:** [direct-llm.ts:146](file:///c:/Users/esenb/Desktop/my_geni/contextos-mcp/src/agents/direct-llm.ts#L146)
- **Суть:** Контекст сканирует и читает файлы рабочей директории в открытый промпт.
- **Риск:** Файлы `.env*`, SSH-ключи (`id_rsa*`) и `*.pem` не отфильтровываются. Написанный модуль [secret-filter.ts](file:///c:/Users/esenb/Desktop/my_geni/contextos-mcp/src/security/secret-filter.ts) по факту **нигде не вызывается**. Список `files` не защищён от относительных путей вида `../../.env` и абсолютных путей операционной системы.

#### 6. Опасные Git-операции и потеря пользовательских данных
- **Локация:** [manager.ts:166](file:///c:/Users/esenb/Desktop/my_geni/contextos-mcp/src/worktree/manager.ts#L166), [merge.ts:27](file:///c:/Users/esenb/Desktop/my_geni/contextos-mcp/src/worktree/merge.ts#L27)
- **Слепой коммит:** Код безусловно выполняет `git add -A`, автоматически коммитя незашифрованные секреты, `.env`, временные логи и сторонние файлы worktree.

#### 7. Неконтролируемый деструктивный Cleanup
- **Локация:** [session.ts:250](file:///c:/Users/esenb/Desktop/my_geni/contextos-mcp/src/mcp/session.ts#L250), [state.ts:176](file:///c:/Users/esenb/Desktop/my_geni/contextos-mcp/src/mcp/state.ts#L176)

#### 8. Опубликованный пакет MCP неработоспособен

### P1 — Серьёзные функциональные дефекты

1. **Режим `sequential` фиктивен:**
   - В [contextos.ts:147](file:///c:/Users/esenb/Desktop/my_geni/contextos-mcp/src/mcp/tools/contextos.ts#L147) все `spawnPromises` создаются через `map()` и стартуют в фоновом пуле одновременно до проверки `mode === "sequential"`. Цикл ожидания лишь последовательно вызывает `await` на уже запущенных параллельных задачах.
2. **Иллюзия асинхронного режима (`wait: false`):**
   - Инструмент возвращает сгенерированный `task_id`, однако в рантайме отсутствует реестр фоновых задач (job registry), опрос их детального прогресса, отмена и восстановление после перезапуска.
3. **Рассинхронизация памяти и персистентного состояния:**
   - После рестарта MCP-сервера сохранённые потоки видны в JSON-логе, но `ThreadManager` в памяти инициализируется с нуля. Операции `diff`, `merge` и `cancel` для таких потоков падают с ошибками.
4. **Жёсткая привязка state к `.swarm-worktrees`:**
   - Состояние сессии всегда пишется в каталог `.swarm-worktrees`, даже если клиент передал кастомный путь размещения worktree.
5. **Гонки записи JSON-состояния (Race Conditions):**
   - Файл состояния читается и перезаписывается без межпроцессных или потоковых мьютексов/lock-файлов. Параллельно завершающиеся агенты перезаписывают изменения друг друга.
6. **Неизолированный кэш результатов:**
   - Ключ кэша задач не учитывает путь к репозиторию, текущий SHA коммита, содержимое файлов и версию промпта. Возможна утечка кэша между разными проектами и возвращение устаревших результатов.
7. **Ложный статус `completed`:**
   - Если выполнение агента завершилось ошибкой, статус потока при определённых путях обработки может ошибочно помечаться как `completed`.
8. **Игнорирование провала верификации:**
   - Отрицательный результат `verify_command` не прерывает последующий конвейер слияния (merge).
9. **Утечка сетевых запросов при `abort`:**
   - `Promise.race` при отмене задачи отсекает ожидание на клиенте, но реальный сетевой HTTP-запрос к провайдеру LLM продолжает выполняться в фоне, расходуя деньги и квоты.
10. **Небезопасный запуск на Windows:**
    - Использование `{ shell: true }` в `spawn` и вызов Claude Code с опасным флагом `--dangerously-skip-permissions`.
11. **Неограниченное накопление stdout/stderr:**
    - Буферы вывода дочерних процессов собираются в память без общего потолка (heap limit), создавая угрозу отказа в обслуживании (OOM DoS).
12. **Коллизии `waitForMessage`:**
    - Ожидание сообщений индексируется исключительно по строковому типу сообщения — два параллельных запроса одного типа затирают обработчики друг друга.

### Анализ системных дефектов и упущений

#### 1. Дефект allowlist-а `verify_command`: Недостаточность `execFile`
- **Проблема:** Запуск `npm test` исполняет произвольное поле `scripts.test` из `package.json`. В недоверенном репозитории это эквивалентно **Arbitrary Code Execution (ACE)**. `npx` способен скачивать и исполнять произвольные пакеты из npm-реестра.
- **Решение:**
  - Отказ от свободной строки команды со стороны клиента. Переход на **типизированные профили верификации** (`verify_profile: "npm-test"`).
  - Жестко зафиксированные параметры исполнения внутри рантайма (например, `npm.cmd test -- --runInBand --watch=false`).
  - **Environment Allowlist:** Полный отказ от передачи `process.env`. В дочерний процесс прокидывается исключительно минимальный доверенный набор: `PATH`, `HOME`, `LANG`, `SYSTEMROOT`, `TEMP`. Никакие маски вида `*KEY*` не гарантируют отсутствие утечек нетипичных переменных.

#### 2. Критический P0: Unrestricted Python Runtime (`runtime.py:252`)
- **Проблема:** В `runtime.py:252` вызывается реальный Python `exec(compiled, _user_ns)` со стандартными `__builtins__`.
- **Риск:** Агент может импортировать `os`, `sys`, `subprocess`, сокеты, обращаться к локальной сети, читать системные файлы хоста. Именование «isolated namespace» вводит в заблуждение.
- **Решение:**
  - Изоляция исполнения в отдельном контейнере (Docker/Podman/gVisor);
  - Либо ограничение процессов через Windows Job Object / restricted security token / cgroups на Linux;
  - Либо полное отключение RLM execution для недоверенных проектов, с заменой на статический AST-анализ или чистый LLM code-generation без выполнения на хосте.

#### 3. Уязвимость проверки `startsWith()` против Sibling-Paths
- **Проблема:** Проверка `path.resolve(wtPath).startsWith(path.resolve(baseDir))` ошибочна:
  `C:\repo-attacker` формально начинается с `C:\repo`.
- **Решение:** Использование `path.relative()`:
  ```ts
  const rel = path.relative(baseDir, targetPath);
  if (rel.startsWith('..') || path.isAbsolute(rel)) {
    throw new SecurityError('Path traversal detected');
  }
  ```
  Плюс канонизация через `fs.realpathSync` для существующих компонентов, запрет симлинков и валидация маркера владения (`.contextos-owner`).

#### 4. Недостаточность проверки `resolveDir`: Отсутствие авторизации
- **Проблема:** Проверка наличия каталога `.git` подтверждает лишь то, что путь является Git-репозиторием. Она **не дает права** MCP-клиенту работать с любым произвольным репозиторием на машине (например, приватными системными или корпоративными проектами).
- **Решение:**
  - Список разрешенных корневых каталогов (`allowed_roots`);
  - Привязка сессии к `defaultDir`, переданной при старте сервера;
  - Проверка, что `.git` может быть файлом (в случае подкаталогов worktree);
  - Проверка симлинков на всех сегментах пути, а не только на корневой папке.

#### 5. Неполная фильтрация секретов (Narrow Egress Protection)
- **Проблема:** Подключение `SecretFilter` только к `direct-llm.ts` оставляет открытыми остальные каналы утечки:
  - интерактивный сканер контекста;
  - загрузчик навыков ContextOS;
  - RLM;
  - эпизодическая память (episodic memory);
  - логи агентов и буферы вывода;
  - сообщения об ошибках (error traces);
  - Git diff и summary;
  - контент внешних плагинов.
- **Решение:**
  - Увеличение глубины сканирования (снятие лимита в 5000 символов, сканирование всего полезного объема);
  - Принцип **Fail-Closed Egress Filter**: любой внешний трафик (отправка в LLM, возврат в MCP-клиент, сохранение в персистентный лог) проходит через единый шлюз очистки секретов.

#### 6. Транзакционная безопасность Git Staging
- **Проблема:** Использование `task.files` недостоверно (агент мог затронуть другие файлы), а добавление всех файлов из `git status` коммитит мусор и секреты.
- **Решение (Строгий 7-шаговый пайплайн):**
  1. Фиксация baseline-состояния перед запуском агента.
  2. Получение списка реально измененных путей после завершения агента.
  3. Проверка каждого измененного пути через каноническую политику путей.
  4. Жесткая блокировка `.env`, ключей, симлинков и файлов, содержащих паттерны секретов.
  5. Сверка измененных файлов с объявленным скоупом задачи.
  6. Стейджинг через `git add --pathspec-from-file` без вызова шелла.
  7. При любом нарушении политики — отказ от коммита и изоляция ветки.

#### 7. Безопасность и подтверждение Cleanup
- **Проблема:** Удаление веток и worktree по возрасту или PID не защищает от удаления активных пользовательских веток или каталогов при коллизии PID.
- **Решение:**
  - Добавление маркера сессии (`session-id.json`) и ownership ID внутри каждого worktree.
  - Использование межпроцессного lock-файла.
  - Поддержка двух режимов: `cleanup --dry-run` и обязательный флаг подтверждения `cleanup --confirm`. Без подтверждения деструктивные операции с ветками запрещены.

#### 8. Корректность запуска `mcp.mjs` и Smoke-handshake
- **Проблема:** Создание простого враппера, вызывающего `main.js`, может приводить к запуску обычного интерактивного режима вместо MCP-сервера (так как `main.ts` ждет подкоманду `mcp` в `argv`). Флаг `--help` не является валидным тестом для MCP-сервера по stdio.
- **Решение:**
  - Точный входной скрипт `bin/mcp.mjs`, который напрямую вызывает `startMcpServer()` либо принудительно подставляет аргумент `mcp` в `process.argv`.
  - Полноценный интеграционный smoke-тест, выполняющий по stdio протокольный handshake `initialize` (JSON-RPC) и ожидающий валидный ответ со списком capabilities в пределах таймаута.

#### 9. Непокрытые функциональные дефекты P1
- **Отсутствие блокировок при записи state:** Добавление кросс-платформенного file locking (`proper-lockfile` или атомарная запись через временный файл + rename).
- **Кэш-ключи без изоляции:** Включение в ключ хэша коммита (`git rev-parse HEAD`), пути репозитория и версии системного промпта.
- **Восстановление после перезапуска:** Реинициализация `ThreadManager` из сохраненного файла `session-state.json`.
- **Защита от OOM:** Лимит на размер буферов `stdout`/`stderr` (rolling buffer до 2MB).
- **Предотвращение Prompt Injection из плагинов:** Статическая проверка и санитизация скачиваемых файлов `SKILL.md`.
