# Bounded Windows glob workaround — experiment

This prototype was subsequently implemented in the adapter; see the separate
[implementation results](ANTIGRAVITY_BOUNDED_ADAPTER_RESULTS.md).

It is possible to express the two previously failing patterns while preserving
their directory boundaries, by replacing each filename `*` with a finite set
of patterns for every possible number of non-separator characters. This is an
experiment using native rule files, not an implementation in the adapter.

On the NTFS test fixture, a filename component is at most 255 characters:
`*.js` needs 253 alternatives for lengths 0–252, and `test*.js` needs 249 for
lengths 0–248. The recursive case needs both direct and nested directory forms,
for 498 alternatives. Each character is constrained to exclude Windows `\`;
the recursive prefix may consume separators only before the final filename.
Microsoft documents the [NTFS filename limit](https://learn.microsoft.com/en-us/troubleshoot/windows-client/backup-and-storage/fat-hpfs-and-ntfs-file-systems#ntfs-naming-conventions).
Other filesystems and namespace limits must be verified separately.

The proof of concept split the 751 alternatives into **47 native rule files**,
totalling **723,479 bytes** including metadata and instruction bodies: 16
files for fixed depth, 31 for the recursive filename prefix. The largest file
was 16,165 bytes, under the [documented 24,000-byte rule limit](https://antigravity.google/docs/rules/).
It did not measure latency or establish production performance.

An upstream `doublestar/v4` 4.10.0 harness checked **2,526 expected outcomes**,
including every ASCII filename length up to the relevant 255-character NTFS
limit, nested paths, similar directory names, wrong extensions, and an emoji.
All matched. This exercises the matcher with synthetic paths; it does not prove
that all those paths can be created, opened or delivered in the IDE.

Live testing used Antigravity IDE 2.5.5 on Windows and Gemini 3.8 Flash High,
with a fresh chat and no rule attachments for each task. The rules used two
independent random markers, one per source pattern, absent from the prompts.
The pre-existing recursive fixture rule also returned its own separate marker
for `src/api/` files. One trial per case is not a reliability estimate.

| File | Fixed-depth `src/api/*.js` | Recursive `src/api/**/test*.js` |
| --- | --- | --- |
| `src/api/test-check.js` | Present | Present |
| `src/api/nested/test-check.js` | Absent | Present |
| `src/api/test-directory/invoice.js` | Absent | Absent |
| `src/other/invoice.js` | Absent | Absent |
| `src/api/<180 z characters>.js` | Present | Absent |

In the last case, the IDE's expanded `Analyzed` step showed the full 183-character
filename matching the request. The model's final Markdown link used a shorter
filename, so the file-read trace, rather than that link, is the evidence for
which file was read.

This approach scales poorly in the number of rules and generated bytes,
especially when patterns or skills multiply. The chunk count also depends on
the size of each actual instruction body. A production adapter would need
deterministic chunk names, owned-file conflict protection, transaction/recovery,
safe pruning, body-size checks, and behavior for paths containing commas and
non-NTFS filesystems. None of those adapter integration behaviors were tested
here. Fixing path normalization in Antigravity remains the cleaner general
solution; a bounded export would be a separate, explicit engineering trade-off.

All experimental rule and fixture files were removed after exact-content and
path checks. The original fixtures matched their expected bytes, export check
passed, and the IDE was reloaded without the temporary rules. The prototype
and compact results are retained in `scratch/antigravity-bounded-globs/`.
No adapter implementation, product commit, push or publication was made in
this experiment.
