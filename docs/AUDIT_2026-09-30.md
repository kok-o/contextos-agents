# Аудит ContextOS — 30 сентября 2026

Это снимок до исправлений на указанном ниже commit. Результаты последующей стабилизации и оставшиеся задачи записаны в [IMPROVEMENT_PLAN.md](../IMPROVEMENT_PLAN.md).

## Вывод

ContextOS решает полезную задачу: хранит правила работы ИИ-агентов в репозитории, проверяет их структуру, собирает конфигурации для разных клиентов и обнаруживает расхождение между исходными инструкциями и сгенерированными файлами. Наиболее убедительная область применения — команды, которые используют несколько агентов и хотят поддерживать общие инструкции и воспроизводимые конфигурации.

В текущем состоянии я не рекомендую выпускать проект как полностью надёжное средство синхронизации пользовательских правил. Воспроизведены потеря пользовательских Copilot-инструкций, игнорирование project overrides и изменения файлов от заявленного read-only MCP status. Эти дефекты важнее увеличения каталога или развития swarm/RLM.

Также проект пока нельзя позиционировать как доказанный способ снизить стоимость длительной сессии Codex. Resolver не включён в обычный экспорт, бюджеты не охватывают весь фактически загружаемый контекст, некоторые адаптеры объединяют дополнительные инструкции и примеры. Историей чата, ответами инструментов и суммарным cached input внешнего клиента core не управляет.

## Что именно делает проект

### Core: конфигурации и инструкции

Публичный CLI находится в `bin/index.js`; локальный `.agents/ctx.js` предоставляет проектные команды. У root-пакета нет внешних runtime npm dependencies; YAML implementation поставляется внутри. Root требует Node >=22.

Источники инструкций — `.agents/core/skills`, установленные plugins, profiles и правила проекта. Важные подсистемы:

1. **Compiler** читает manifests, нормализует метаданные, считает hashes содержимого/ресурсов и формирует `.agents/compiled/registry.v2.json`.
2. **Resolver** оценивает задачу по keywords, файловым globs, workspace dependencies, phase и risk. Затем применяет зависимости/conflicts и планирует набор skills с оценкой размера.
3. **Adapters** создают client-specific файлы. Pure rendering отделён от записи; application использует lockfile, project locks и журналируемые транзакции.
4. **Drift detector/gate** сравнивает ожидаемые артефакты с диском и lockfile: отсутствующие, изменённые, устаревшие, orphan и ошибки конфигурации.
5. **Scanner/hooks** проверяют предусмотренные паттерны и staged Git blobs. Это полезная профилактика, но regex scanner не является полноценным анализом безопасности приложения.
6. **Catalog/plugins** позволяют добавлять domain skills, включая React, FastAPI и другие технологии. Для сторонних источников есть проверки путей, provenance и механизмы закрепления/обновления.

Реальный поток не равен обещанию «resolver автоматически выбирает минимальный контекст перед каждым экспортом»:

```text
core / plugins / profiles
    ├── compiler ── compiled registry ── resolve(task) ── рекомендация skills
    └── adapters: перечисление установленных skills ── rendering ── apply / lockfile
                                                                    └── drift / gate
```

`.agents/adapters/shared.js` получает все доступные core/plugin directories и исключает skills по profile. Обычный экспорт не вызывает canonical resolver с задачей. Полученный через `resolve` список сам по себе не уменьшает экспортируемые правила.

### MCP и экспериментальное исполнение

`contextos-mcp` — отдельный TypeScript/ESM пакет. В нём находятся MCP server, sessions, budget tracking, backend adapters, threads/worktrees, verification/reviewer pipeline и экспериментальные swarm/RLM/labs компоненты.

Default live server зарегистрировал только `contextos_status`, `contextos_compare`, `contextos_diff`. Вызов status открывает runtime session. Документация о context resolver/explain и default read-only boundary не совпадает с этим интерфейсом.

Наличие runtime budget, sandbox и reviewer pipeline не означает, что ContextOS контролирует расходы и действия независимой сессии Codex Desktop. Это механизмы собственного runtime и интеграций, которые должны быть явно подключены и проверены.

## Для чего ContextOS нужен

| Сценарий | Практическая польза | Ограничение |
| --- | --- | --- |
| Несколько AI clients в одной команде | Общие правила и повторяемые exports | Требуется подтвердить реальные native loader contracts |
| Несколько репозиториев | Версионирование навыков, profiles, управляемые обновления | Overrides сейчас не проходят до consumers |
| CI для AI configuration | Обнаружение drift и ошибки конфигурации | `gate` не подтверждает качество кода самого приложения |
| Управление каталогом skills | Метаданные, manifests, зависимости и provenance | «Валидирован» не равно «улучшает результат агента» |
| Выбор контекста под задачу | Resolver предлагает релевантные skills | Экспорт и внешний клиент не используют выбор автоматически |
| Исполнение нескольких агентов | Экспериментальная orchestration инфраструктура | Требует отдельного hardening и эксплуатационного измерения |

Для одного Codex-пользователя с одним репозиторием польза менее очевидна: короткий root AGENTS.md и несколько skills по запросу могут выполнять большую часть нужной функции. Это инженерная оценка сложности, а не измеренный сравнительный результат.

## Подтверждённые проблемы

Приоритет P1 означает существенный нарушенный контракт: потеря данных, игнорирование пользовательских правил или нарушение заявленной границы записи. P2 — функциональные ошибки, ограничения совместимости и факторы стоимости. Это приоритет ремонта, а не шкала CVSS.

### P1-1. Copilot export удаляет пользовательские инструкции

**Воспроизведение:** в новом consumer создать `.github/copilot-instructions.md` с уникальным пользовательским правилом и выполнить `export copilot`. Команда возвращает exit 0 и сообщение об успешном экспорте; пользовательского маркера в результате нет. Повторено на свежем распакованном npm tarball.

**Причина:** `.agents/adapters/copilot/export.js` формирует полный новый файл. `.agents/adapters/pure-compiler.js:263-283` сравнивает hashes/lock records и пишет artifact, но не защищает уже существующий unmanaged файл от захвата и перезаписи. Транзакционность не предотвращает семантическую потерю пользовательских данных.

**Исправление:** общий ownership contract для adapters. Незнакомый файл должен сохраняться либо требовать явной операции принятия под управление; собственный контент лучше размещать в managed block. При обновлениях нужны preconditions для изменённых файлов. Конкретно воспроизведена потеря Copilot-файла; аналогичные риски остальных adapters требуют собственных probes.

**Приёмка:** исходное пользовательское правило сохраняется после первого и повторного экспорта; локальная правка управляемого файла не исчезает молча; отказ не оставляет частичных изменений.

### P1-2. Override создаётся, но compiler и adapters его игнорируют

**Воспроизведение:** `skill override security` успешно создаёт `.agents/project/skills/security`. После добавления маркера в его SKILL.md, `compile` и `export all` также успешны. `sourceGraphHash` не изменяется; маркера нет в Gemini skill, Claude generated skill и Cursor security rule.

**Причина:** `.agents/customization-dx.js:47` создаёт project override, но compiler discovery (`manifest-compiler.js:655-689`) и exporter discovery (`plugins.js:1224`) читают другие наборы директорий. Кроме того, override копирует только файлы верхнего уровня и не переносит вложенные resource directories.

**Последствие:** пользователь уверен, что адаптировал security/workflow rules, а агент получает upstream-вариант. Проверки создания директорий этого не обнаруживают.

**Исправление:** единый effective skill registry с явным precedence для project override, vendor/core и plugins. Его должны использовать compile, resolve, export, hashes и diagnostics. Включить перенос и валидацию resources.

**Приёмка:** уникальная project-инструкция видна в compiled entry, resolver и каждом поддерживаемом consumer; исходные core-файлы остаются неизменными; delete override возвращает upstream-поведение.

### P1-3. Default MCP status изменяет репозиторий

**Воспроизведение:** server запущен без `--enable-runtime` в пустом Git repo. До status была только `.git`; после появились `.agents`, `.swarm-worktrees` и `.gitignore`.

**Причина:** `contextos-mcp/src/mcp/tools/contextos.ts:398` вызывает `getSession`; `src/mcp/session.ts:175` инициализирует thread manager. `src/worktree/manager.ts:189-210` создаёт worktree directory и изменяет `.gitignore`.

**Исправление:** read-only query layer должен читать существующее состояние без runtime init. Инициализация session/worktree допустима только при явно включённом runtime и соответствующей команде.

**Приёмка:** initialize/list/status/compare/diff в default mode не изменяют дерево файлов или Git state, включая пустой проект. Отдельно тестировать каждый read-only tool.

### P2-1. Первый успешный export all сразу проваливает check/gate

**Воспроизведение:** `init → export all → export all --check --json → gate --json`. Export успешен, обе проверки возвращают 1. Finding — `STALE_INPUT` для `.aider.conf.yml`.

**Причина:** `.agents/adapters/aider/export.js:72-94` создаёт первый YAML из шаблона с комментариями, а существующий файл читает/сериализует через YAML. Следующая проекция удаляет комментарии и меняет формат. Проверка двух вызовов pure render до применения не покрывает переход «файл отсутствует → файл существует».

**Исправление/приёмка:** единая сериализация и тест ровно одного export на пустом consumer: сразу после него check/gate должны возвращать 0. При этом значения пользовательской конфигурации должны сохраняться.

### P2-2. Бюджет resolver не является полным ограничением контекста

**Воспроизведение:** `resolve "Fix typo in README" --budget 1000 --json` возвращает `totalEstimatedTokens: 4895`, два foundation skills и `warnings: []`.

**Причина:** canonical resolver исключает `BASE_SKILLS` из allocated dynamic budget (`canonical-resolver.js:1003-1092`), затем добавляет их в итоговый набор. Mandatory dependencies допускаются с soft-budget semantics. В бюджет не входят общий AGENTS.md, системные инструкции клиента, история, tool outputs и дополнительный текст экспортов.

Compiler оценивает в основном entrypoint body; exporters могут добавить EXAMPLES/TROUBLESHOOTING. Разные слои также имеют разные defaults бюджета. Поэтому `--budget` и описание «prevent token overflow» создают слишком сильное ожидание.

**Исправление:** назвать и документировать hard/soft budgets; считать полную выбранную проекцию вместе с foundation/bootstrap/resources; выдавать предупреждения при любом превышении. Подключить task-based выбор к реальному consumer pipeline, иначе его экономический эффект ограничивается советом агента.

### P2-3. Адаптеры теряют вложенные resources и укрупняют skills

Gemini export объединяет SKILL.md с дополнительными Markdown, включая examples и troubleshooting; Claude делает сходное объединение. При этом вложенные `references` не копируются. Например, core context-manager имеет `references/context-rules.md`, но generated/native alias skill не содержит этот файл, хотя SKILL ссылается на него относительно себя.

**Причина:** `.agents/adapters/gemini/export.js:45-106` и Claude renderer работают преимущественно с отдельными Markdown-файлами и экспортируют SKILL.md. Это не полноценная проекция resource tree.

**Исправление:** сохранять короткий entrypoint, переносить declared resources с безопасными путями и читать examples/references по запросу. Acceptance должен разрешать каждую локальную ссылку именно из установленного skill directory.

### P2-4. Native integration и структурный экспорт смешаны

Официальные client docs сверены во время аудита. Проверки наличия выбранных выходных файлов не доказывают загрузку этих файлов клиентом.

| Клиент | Что генерирует проект | Оценка |
| --- | --- | --- |
| Gemini CLI | `.agents/skills/*/SKILL.md` | Это поддерживаемый workspace alias; остаются проблемы resources и объёма |
| Claude Code | Root CLAUDE.md + `.agents/generated/claude/skills` без YAML frontmatter | Root instructions/index могут работать, но это не стандартная native project skills directory `.claude/skills` |
| Cursor | `.cursor/rules/*.mdc` | Формат соответствует rules; alwaysApply вызывает постоянную загрузку выбранных длинных rules |
| Zed | `.zed/rules.md`, `.zed/prompts/*` | `.zed/rules.md` отсутствует в текущем documented list project instruction files; standalone native auto-load не подтверждён |
| Copilot | `.github/copilot-instructions.md` | Стандартный путь, но подтверждена потеря пользовательского содержимого |
| Aider | CONVENTIONS + `.aider.conf.yml` | Предусмотренная интеграция через read; первый export не идемпотентен |
| Codex | Специального адаптера нет; `.agents/AGENTS.md` | Root instruction loader не обнаруживает произвольный вложенный файл этого имени; отдельные skills могут обнаруживаться независимо |

Default init синхронизирует Gemini, но финальный banner обещает автоматическую загрузку `.agents/AGENTS.md` для открываемого AI assistant. Это обещание требует уточнения по каждому клиенту.

Источники: [Codex AGENTS discovery](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [Gemini skills](https://geminicli.com/docs/cli/using-agent-skills/), [Claude skills](https://code.claude.com/docs/en/skills), [Cursor rules](https://cursor.com/docs/rules), [Zed instructions](https://zed.dev/docs/ai/instructions).

**Исправление:** compatibility matrix должна различать native loader, manual index и structured export. Нужны client acceptance scenarios: установка → запуск → уникальное правило реально влияет на ответ или видно в loader diagnostics. Для Codex стоит сделать короткий root AGENTS.md, учитывающий пользовательское содержимое.

### P2-5. Установленный standalone plugin отсутствует в compiled registry

**Воспроизведение:** `skill add fastapi` создаёт `.agents/plugins/fastapi/SKILL.md`, но `compile` оставляет 7 core entries без FastAPI.

**Причина:** compiler перечисляет только `.agents/plugins/<plugin>/skills/*`, а `collectAllSkillDirs` и установка поддерживают также standalone layout. Resolver способен обнаружить plugin другим путём, что скрывает рассогласование и даёт fallback metadata/оценки.

**Исправление/приёмка:** один discovery contract для standalone и bundle; entry, hashes, estimated size, resolver и adapter outputs должны ссылаться на один installed source. Проверять обе формы через публичную CLI из tarball.

### P2-6. Windows dev launcher MCP не запускается без dist

В изолированной копии без ignored dist handshake test завершается `spawn EINVAL`. `contextos-mcp/bin/mcp.mjs:53` непосредственно запускает `tsx.cmd` через `spawn` на Windows.

**Исправление:** запускать Node entrypoint tsx или использовать проверенный cross-platform launcher с корректной обработкой аргументов. Acceptance — clean checkout на Windows, без заранее созданного dist. Это дефект development fallback; отдельно собранный пакет с dist использует другую ветвь.

### P2-7. Gate и verification claims требуют более точного смысла

`bin/lib/gate.js:31` проверяет adapter drift. Он не запускает tests/typecheck приложения, не проверяет архитектуру или корректность authentication и не доказывает production quality. Тексты про «production quality gate» шире фактического контракта.

Наличие rule вроде TEST-001 и подключённого validator также не доказывает, что нужные приложению tests были выполнены: проверка skill frontmatter подтверждает структуру инструкции. Аналогично catalog validation и claims lint не подтверждают полезность всех skills или универсальное повышение качества.

Позитивно, что token-reduction claim отмечен invalidated. Оставшиеся стопроцентные результаты на небольших наборах не следует обобщать на будущие задачи. Нужны сырые per-task результаты, baseline, независимая оценка и корректные интервалы неопределённости.

В документации также встречаются отсутствующие package scripts: `benchmark`, `benchmark:chat:pack`, `benchmark:chat:eval`. Есть benchmark implementations, но это не делает устаревшие команды рабочими.

**Исправление:** точные названия и documented contracts; автоматическая проверка runnable commands; разделение «структурно проверен», «пример выполнен», «client loader проверен» и «эффект на результат измерен».

## Контекст и стоимость длительной сессии

Да, проект способен заметно увеличить стартовый и повторно используемый контекст. Особенно это относится к always-on rules и чтению skills, в которые export добавил examples/troubleshooting.

Локальные приближённые размеры по символам, а не по model tokenizer:

- `.agents/AGENTS.md`: 18 205 символов, примерно 4 551 tokens при делении на 4.
- Общий AGENTS + bodies семи core skills: примерно 16,9 тыс. tokens.
- AGENTS + соответствующие расширенные generated skill bodies: примерно 20,9 тыс. tokens.
- Набор четырёх Cursor alwaysApply rules и project rule: примерно 15,9 тыс. tokens.

Это размеры конкретных наборов файлов; они **не означают**, что каждый клиент автоматически отправляет все эти файлы при каждом запросе. Нужны loader/usage traces. В Codex каталог metadata и skill body, прочитанный по запросу, имеют разное влияние.

209 млн input в длительной сессии — накопленный учёт многих запросов. Это не размер одного context window. Даже cached input тарифицируется при повторных обращениях; поэтому большой сохраняемый prefix и большое число шагов могут давать существенную стоимость. Нельзя приписать весь расход $55 ContextOS без сопоставления request usage и контрольной сессии.

В ранее проверенных журналах указанной сессии были 1 504 обновления usage по пяти связанным rollout logs, 209 158 710 input и 206 346 670 cached input. Это объясняет масштаб повторного чтения. Реконструкция точного денежного счёта и причинная доля ContextOS в этом аудите не выполнены.

Для экономии нужно исправить consumer pipeline, а затем измерить эффект:

1. Bootstrap около 500–1000 tokens как проектная цель, без длинных ролей/ритуалов для каждой задачи.
2. Metadata/index всегда, skill body по необходимости; examples/references по запросу.
3. Один effective registry и выбор skills под текущую задачу до загрузки в клиент.
4. Телеметрия request count, uncached/cached/write input, output и стоимости по модели; метрики самого ContextOS отдельно от внешнего клиента.
5. Размеры tool outputs, повторных reads и compactions; контрольная одинаковая задача с минимальными инструкциями и с ContextOS.
6. Критерий — стоимость успешно принятого результата и качество результата, а не только число символов или cache-hit процент.

## Что уже сделано хорошо

- Компилятор, hashes, drift taxonomy и отделение rendering/application дают содержательную основу воспроизводимой конфигурации.
- Project locks, safe-path checks, journaled transactions и negative tests лучше простого копирования Markdown скриптом.
- Нулевая внешняя runtime dependency surface root-пакета упрощает потребительскую установку.
- Есть тесты tarball/install/CLI/hooks, а не только проверки исходников. Полный core прогон сейчас действительно проходит.
- Каталог имеет manifests, связи, структурную валидацию и отдельную проверку некоторых исполняемых примеров.
- Claims governance допускает invalidated measurements. Это лучше сохранения неподтверждённого обещания экономии.

## Что улучшать и в каком порядке

### Этап 1. Надёжность пользовательских данных

Сначала P1: ownership/merge/preconditions, effective registry overrides, read-only MCP. Затем Aider idempotence и standalone plugins. Реалистичный критерий завершения — публичные consumer scenarios из свежего tarball с уникальными пользовательскими маркерами. Результат должен проверяться через конечный сгенерированный файл, а не только наличие override directory.

### Этап 2. Честная и работающая совместимость

Уточнить init target, исправить banner, native paths/frontmatter/resources, отдельно реализовать Codex integration. В CI добавить Windows и Linux clean checkout, fresh package install и client-specific acceptance там, где клиент допускает такую проверку. Успешное создание `.zed/rules.md` не считать native compatibility evidence.

### Этап 3. Минимальный контекст и измеримый результат

Упростить default bootstrap; сделать общий бюджет действительно полным для предоставляемой проекции; убрать дубли и bulk examples из entrypoint; применить resolver в consumer pipeline. Затем собрать сравнение на одинаковых задачах: accepted result, failures, tool steps, latency, ordinary/cached input и стоимость. До этого не обещать фиксированный процент экономии.

### Этап 4. Снизить сложность проекта

Закрепить одно ядро discovery/compile/resolve/export. Устранить параллельные реализации init: публичная CLI и `.agents/init/init-engine.js` используют разные наборы, при этом второй модуль не входит в root tarball. Удалять только после проверки references и тестов.

Развести стабильный compiler/configuration product и experimental runtime/labs: отдельные release contracts, тесты и документация. Сейчас roadmap/runtime шире самого надёжного сценария «сохранить пользовательские инструкции и синхронизировать клиентов».

### Этап 5. Продуктовая проверка

Лучший начальный фокус — multi-agent teams и конфигурационный drift. Нужны несколько реальных pilot repos, зафиксированные проблемы до внедрения и измерение после. Полезные метрики: время настройки второго клиента, конфликты/потери rules, число drift incidents, размер загружаемых instructions и стоимость принятой задачи.

Не измерены коммерческий спрос, willingness to pay и качество генерации на независимом наборе. Эти результаты нельзя получить из unit tests. Расширение каталога до устранения consumer defects увеличит поддержку быстрее, чем подтверждённую пользу.
