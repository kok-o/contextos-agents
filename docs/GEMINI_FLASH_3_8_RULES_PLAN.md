# План усиления правил и skills для Gemini 3.8 Flash

## Цель и границы

Точечно уточнить существующие инструкции против пяти типов сбоев: выдуманные API, остановка на плане, неполная реализация, повторение неудачных действий и неподтверждённое «готово». Не переписывать то, что уже достаточно конкретно; при уточнении заменять старую формулировку, а не добавлять её дубль.

Это план улучшения инструкций, а не изменения модели. Перечисленные сбои — целевые сценарии для правил, а не утверждение об их измеренной частоте у Gemini 3.8 Flash.

В этой итерации не менять runtime, MCP, архитектуру адаптеров и каталог. Не добавлять новые skills, если правило относится к существующему. Не запускать платные API-прогоны, не публиковать пакет и не создавать коммиты без отдельного запроса.

Канонические изменения вносить в исходные bundles. `.agents/skills/`, `.agents/generated/` и другие управляемые проекции не править вручную. Не затрагивать посторонние изменения, включая существующее удаление `.agents/plugins/contextos/hooks.json`.

## Критерии готовности

- Запрос на реализацию отличается от вопроса, обсуждения и просьбы написать план: последние не разрешают автоматически менять приложение.
- Незнакомые символы, зависимости и команды проверяются до использования; непроверенное предположение не описывается как факт.
- План, заглушка, неподключённая функция и успешная структурная проверка не подменяют завершённую реализацию.
- После ошибки агент проверяет результат и состояние, прежде чем повторять потенциально изменяющую данные операцию.
- Проверки соответствуют риску, обнаруживают исходный баг, когда это применимо, и не заменяются пересказом намерений.
- Финальный отчёт различает выполненное, проверенное и заблокированное; не требует громоздкой формы для простой задачи.
- Инструкции не ослабляют безопасность, не требуют бесконечных повторов и не создают лишних остановок ради согласований.
- Источники, примеры, troubleshooting и экспорты согласованы. Локальные тесты проверяют только свой фактический контракт и не выдаются за доказательство улучшения модели.

## Этап 0. Зафиксировать пробелы и сценарии до изменения правил

### Инвентаризация «уже есть → чего не хватает → где исправить»

Исходная карта по текущим документам; перед реализацией перепроверить её по актуальной версии файлов.

| Уже есть | Недостающая конкретика | Основное место правки |
| --- | --- | --- |
| Проверка экспорта, сигнатуры, версии и вызывающего кода | Не повторять правило; проверить его доступность при выборе skill | `gemini-precision/SKILL.md` и проверка экспортов |
| Реализация интеграций целиком; прямой вопрос без полного workflow | Явно отличить запрос на реализацию от обсуждения и плана | `engineering-workflow/SKILL.md`; короткое отражение в `GEMINI.md` |
| Проверка состояния после ошибки перед повтором записи | Проверка точного объекта при неоднозначном результате и смена гипотезы при повторной ошибке | `gemini-precision/SKILL.md` и `TROUBLESHOOTING.md` |
| Минимализм с сохранением безопасности и необходимых проверок | Не сокращать требования; проверять необходимое подключение и конфигурацию | `ponytail-mindset/SKILL.md` |
| Запрет выдавать stub за интеграцию, регрессионные проверки, сверка diff | Сохранить; добавить только недостающий пример ложного завершения | Существующие workflow и `gemini-precision/EXAMPLES.md` |
| Отчёт о командах, результатах и ограничениях | Не создавать новый обязательный формат и не дублировать существующий | Существующий workflow |
| Экспорт skill entrypoints, ресурсов и правил активации | Корневой `GEMINI.md` не экспортируется Gemini-адаптером; значимые изменения нужны в канонических skills | Проверка `.agents/adapters/gemini/export.js` без изменения адаптера |

### Сценарии и исходное состояние

До правок правил сохранить исходную ревизию и точный diff рабочего дерева, копии используемых инструкций и их хеши. Подготовить одинаковые задания и независимые критерии для будущего сравнения старых и новых инструкций:

| Задание | Проверяемый результат |
| --- | --- |
| Убедительно названный, но отсутствующий в проекте API | Нет выдуманного импорта; вывод опирается на проверку проекта |
| Запрос небольшой реализации | Есть изменение и релевантная проверка, а не только план |
| Изменение, требующее обновить вызывающий код | Необходимая цепочка подключения работает |
| Падающая проверка | Причина исправлена; тест не отключён ради завершения |
| Неоднозначный результат записи | Состояние проверено; дубликат не создан |
| Реальный блокер | Блокер назван точно; доступная независимая часть выполнена |
| Обычный вопрос | Нет незаказанных изменений и лишних согласований |
| Исправление опечатки | Нет ненужного полного цикла и несвязанных правок |

Заранее определить фиксацию ошибок, лишних действий, ненужных вопросов, ручных вмешательств и доступных данных о времени, usage и затратах. Недоступные метрики оставлять неизвестными, не подменять их оценкой по длине текста. Условия будущего сравнения должны совпадать по модели, настройкам, инструментам и исходным fixtures; историю диалога не переносить между вариантами. Критерии оценки не подсказывать модели в задании.

**Выход этапа:** проверенная карта пробелов, исходный снимок и зафиксированные сценарии. Запуски модели и платные вызовы этим этапом не разрешаются.

## Этап 1. Собрать короткий обязательный контракт

**Файлы:** `GEMINI.md`, при необходимости общие положения в `.agents/AGENTS.md`.

Вместо новых слоёв инструкций собрать компактное ядро из существующих требований и одной явной границы между реализацией и обсуждением. Общее правило разместить в каноническом workflow; `GEMINI.md` использовать как краткое руководство этого checkout, а не как единственный канал доставки:

1. Определи тип запроса и требуемый результат.
2. Прочитай затрагиваемый код, определения и вызывающие участки.
3. Если запрошена реализация — выполни её, а не только опиши.
4. Проверь поведение доступными средствами.
5. Сообщи фактический результат и ограничения.

Для реализации остановка допустима после выполнения критериев либо при конкретном блокере: отсутствуют права, обязательное решение пользователя, доступ или необходимая среда. Перед передачей блокера выполнить независимую доступную часть работы. Не обходить запрет и не совершать опасные действия ради завершения.

**Проверка:** вопрос не запускает редактирование; запрос на код не заканчивается одним планом; существующее разрешение не запрашивается заново после смены этапа. Общий entrypoint не получает необоснованных утверждений о конкретной модели.

## Этап 2. Сделать gemini-precision набором процедур

**Файлы:** `.agents/core/skills/gemini-precision/SKILL.md`, `EXAMPLES.md`, `TROUBLESHOOTING.md`; metadata и `VALIDATION.json` — только при реальной необходимости.

Добавить только недостающие переходы из инвентаризации этапа 0. Уже существующие проверки API, интеграции и осторожность после ошибки сохранить без повторного изложения. Таблица ниже — контроль покрытия, а не требование вставить все строки в skill:

| Ситуация | Требуемое действие |
| --- | --- |
| Незнакомый импорт или метод | Найти определение/экспорт, проверить установленную версию, сигнатуру и применимый пример использования |
| Символ не найден | Проверить другие реальные источники; не изобретать пакет, путь или контракт |
| Инструмент завершился ошибкой | Прочитать ошибку, выяснить последствия и выбрать следующий шаг по новой информации |
| Повторно возникает та же ошибка | Не повторять неизменённый подход без основания; сменить проверяемую гипотезу или способ диагностики |
| Результат записи неоднозначен | Прочитать состояние точного целевого объекта перед повтором, чтобы не дублировать действие |
| Заявлена работающая интеграция | Проверить необходимую цепочку вызова и соответствующий эффект, а не только изолированный helper |

Добавить несколько коротких пар «неправильно / правильно» только для новых процедур. Не устанавливать универсальное число повторов: учитывать временные ошибки, стоимость, идемпотентность и безопасность.

**Проверка:** каждая процедура заканчивается наблюдаемым критерием, а не фразой «будь внимательнее». Примеры не имитируют доступные API или результаты инструментов.

## Этап 3. Закрыть преждевременное завершение и недоделки

**Файлы:** `.agents/core/skills/engineering-workflow/SKILL.md`, `references/workflow.md`, `.agents/core/skills/ponytail-mindset/SKILL.md`, при необходимости `references/minimalism.md`.

Закрепить разделение ответственности:

- Workflow отвечает за доведение авторизованной задачи до результата и проверку.
- Ponytail отвечает за минимальную сложность без сокращения требований.
- Gemini-precision отвечает за проверку предположений и дисциплину работы с инструментами.

Для изменения поведения проверить нужные точки подключения, конфигурацию, ошибки и затронутые вызовы — только там, где они действительно необходимы. Не превращать это в обязательное добавление всех слоёв к любой задаче.

Для завершения перечислить про себя или в коротком плане критерии задачи и сопоставить их с результатом. Не требовать отдельного отчёта или нового файла для мелкой правки.

**Проверка:** реализация без необходимого подключения не считается готовой; достаточное локальное исправление не разрастается в лишнюю архитектуру; mock допустим для проверки интерфейса, но не доказывает внешний эффект.

## Этап 4. Согласовать существующие проверки и примеры

**Файлы:** существующие workflow и примеры `gemini-precision`.

Не переписывать существующие требования к регрессионным проверкам, сверке diff, запрету заглушек и отчёту. Сверить примеры и troubleshooting с уточнёнными процедурами; исправить только расхождения. Не добавлять новый обязательный чек-лист, если тот же критерий уже покрыт workflow.

**Проверка:** отдельно разобрать ложные доказательства: успешный запуск команды без проверки поведения, тест только mock-объекта, пустой staged scan и текст вызова инструмента вместо его выполнения. Самопроверку не называть независимым review.

## Этап 5. Убрать дубли и проверить доставку

**Файлы:** затронутые исходные bundles и manifests; тесты selection/export — по необходимости.

- Сохранить одно основное место для каждого правила; в остальных местах оставить короткое указание без копирования целой процедуры.
- Не загружать длинные примеры и troubleshooting на каждую простую задачу.
- Сохранить минимальный обязательный контракт; предметные детали подключать по задаче.
- Проверить описание и условия выбора `gemini-precision`, не превращая его в обязательный процесс для опечаток и прямых вопросов.
- Проверить, какие изменения действительно попадают в экспорты: Gemini-адаптер формирует `.agents/generated/gemini/skills/`, `.agents/skills/`, ресурсы и, в зависимости от активации, `.agents/rules/`. Корневой `GEMINI.md` не является экспортируемым артефактом; значимые правила должны быть в канонических skills.
- При обнаружении проблемы доставки зафиксировать её отдельно; не расширять эту итерацию до переписывания адаптеров.

**Проверка:** обновлённое правило существует в нужном управляемом выводе; export check не обнаруживает drift. Это подтверждает файл-контракт, но не чтение или соблюдение правила моделью.

## Этап 6. Проверить изменения без подмены доказательств

### Локальные проверки

Использовать существующие тестовые точки: `tests/core-skill-standard.test.js`, `tests/skill-examples.test.js`, `tests/focused-context.test.js`; selection/export-тесты расширять только при изменении соответствующего контракта.

Последовательность после реализации:

1. Целевые тесты изменённых контрактов.
2. `npm run test:skills` и `npm run lint:md`. Дополнительно явно проверить Markdown корневых инструкций и плана: `npm exec --no -- markdownlint GEMINI.md .agents/AGENTS.md docs/GEMINI_FLASH_3_8_RULES_PLAN.md --config .markdownlint.json`. Для остальных затронутых Markdown-файлов вне охвата npm-скрипта также передать точные пути в markdownlint.
3. `npm run build` и `npm run validate`.
4. `node .agents/ctx.js export all --check --json`.
5. `npm test` перед итоговой передачей изменений.
6. Проверка diff и сохранности посторонних изменений.

Проверки структуры документа и наличия формулировок называть структурными. Выполнение примеров называть проверкой примеров. Ни то ни другое не доказывает, что Gemini лучше решает реальные задачи. Не добавлять жёсткие проверки точного текста там, где нужен устойчивый контракт.

### Граница будущей живой проверки

Использовать задания и критерии, зафиксированные на этапе 0, без подгонки под полученные ответы. При отдельном разрешённом запуске сохранять исходные ответы и действия, настройки среды, вмешательства человека и результаты независимых проверок. Отсутствие улучшения или появление новых лишних действий — основание пересмотреть либо убрать добавленное правило, а не наращивать инструкции автоматически. Без таких прогонов итог этой итерации — согласованность и доставка правил, не доказанное повышение надёжности Gemini.

## Результат итерации

Проверенная карта пробелов, заранее сохранённые сценарии, несколько точечных уточнений существующих skills, короткое отражение в `GEMINI.md`, согласованные примеры и актуальные экспорты. Объём правок определяется найденными пробелами, а не числом этапов; масштабная перепись bundles не требуется. Результаты локальных проверок и непроверенное поведение модели указывать отдельно.
