# Живая проверка ContextOS в клиенте

Сценарий проверяет обнаружение, загрузку и применение экспортированного правила.
Это проверка подключения, а не оценка общего качества модели. Ориентир —
30–60 минут на один клиент; начни с привычного клиента, затем повтори во втором.
Нужны Node.js 22+, npm, Git, доступ к выбранной модели и подготовленный архив core.
MCP для этого сценария не требуется. Скрипт подготовки не вызывает модели.

## 1. Подготовка

Запусти в PowerShell из checkout ContextOS. Архив 2.3.1 появится после подготовки
релиза; до этого можно указать другой проверенный локальный core-архив.
Не используй неприкреплённый `latest` для воспроизводимого результата.

```powershell
node scripts/prepare-live-client-check.cjs scratch/release-candidate/contextos-agents-2.3.1.tgz
```

Скрипт создаёт новую папку в TEMP и печатает путь. В ней четыре самостоятельных
Git-проекта: `negative`, `explicit`, `automatic`, `unrelated`, а также `evidence`.
Для каждого клиента запусти подготовку заново: получится другой контрольный маркер.
Открывай в клиенте только один проект, например `.../explicit`, а не общую папку.
Не прикладывай эту инструкцию, `evidence`, соседние проекты или предыдущие ответы
к проверяемому чату. Иначе контрольный маркер может попасть в контекст обходным путём.

В `evidence/setup.json` автоматически сохраняются версия Node, версия core,
SHA-256 архива, manifest и правил, пути проектов и ожидаемый маркер. Допиши в
`results-template.json`: точное название и версию клиента, модель, reasoning effort,
ОС, время настройки и влияющие глобальные инструкции, plugins и память.
Версию GUI бери из About; версию CLI — из `codex --version` или `gemini --version`.
Не меняй модель и её настройки между условиями. Глобальные настройки должны быть
одинаковыми; ошибки и дополнительные попытки сохраняй, а не заменяй удачным ответом.

В fixture есть `skill.yaml` с описанием назначения правила. В опубликованном
архиве 2.3.1 экспорт одного SKILL.md без manifest давал общее fallback-описание,
поэтому такой вариант не покрывается этим прогоном. В рабочей версии исправлено
сохранение описания из frontmatter; локальные тесты экспорта ещё не доказывают
автоматическое применение исправленного варианта живым клиентом.
Ожидаемый маркер находится только в теле правила, а не в его метаданных.

## 2. Обнаружение и выбор правила

В проекте `explicit` ищи `ctx-live-probe` в списке skills/rules клиента.
Сохрани снимок списка или текст диагностики с путём. Наличие файла на диске
подтверждает экспорт, но ещё не подтверждает обнаружение клиентом.

| Клиент | Что проверять | Явное подключение |
| --- | --- | --- |
| Codex | `.agents/skills/ctx-live-probe/SKILL.md` в доступных skills | Выбрать `$ctx-live-probe` в чате |
| Gemini CLI | `/skills list`; при необходимости `/skills reload` | Попросить использовать skill `ctx-live-probe`; сохранить событие активации и решение в диалоге разрешения |
| Cursor | `.cursor/rules/ctx-live-probe.mdc` в Project Rules | Выбрать правило через `@ctx-live-probe` |

Способы discovery/активации сверены 4 октября 2026 года по официальным документам:
[Codex skills](https://learn.chatgpt.com/docs/build-skills),
[Gemini CLI skills](https://geminicli.com/docs/cli/using-agent-skills/),
[Cursor rules](https://cursor.com/docs/rules).
Если в твоей версии интерфейс отличается, зафиксируй это как результат.
Если после экспорта правило не видно, перезапусти клиент и запиши этот шаг.

## 3. Четыре независимых прогона

Каждое условие запускай в новом чате без истории других условий. Желательно сначала
выполнить отрицательный контроль. Для CLI запусти новый процесс из нужного проекта.
Для автоматического прогона не открывай SKILL.md в редакторе и не прикрепляй его:
открытый файл тоже может попасть в контекст. Не проси агента искать контрольный маркер.

Одинаковый запрос для `negative` и `automatic`:

```text
Реализуй в src/status.cjs синхронную функцию getStatus(), экспортированную через
CommonJS. Она должна возвращать объект с полем ok: true. Без внешних зависимостей.
Проверь результат вызова функции.
```

В `explicit` используй тот же запрос с явным выбором `ctx-live-probe` способом
из таблицы. Для Gemini добавь только: «Используй skill ctx-live-probe».
Не копируй тело правила или ожидаемое значение `source` в запрос.

В `unrelated` отправь другой запрос, без упоминания skill:

```text
Создай src/sum.cjs с CommonJS-экспортом чистой функции sum(a, b), которая
складывает два числа. Проверь sum(2, 3). Другие исходные файлы не меняй.
```

После окончания каждого прогона сохрани весь диалог с инструментальными действиями
или доступный export/transcript, исходные файлы и ошибки. Затем сам выполни в
терминале проекта, отдельно от проверяемого чата:

```powershell
node -p "JSON.stringify(require('./src/status.cjs').getStatus())"
```

Для `unrelated` дополнительно:

```powershell
node -p "require('./src/sum.cjs').sum(2, 3)"
```

| Условие | Ожидаемое поведение |
| --- | --- |
| negative | `ok: true`, контрольного маркера из setup.json нет; skill отсутствует |
| explicit | `ok: true` и `source` точно равен expectedMarker из setup.json |
| automatic | То же, без явного упоминания skill; отдельно записать способ загрузки |
| unrelated | Результат 5; status.cjs остался исходным (`ok: false`); правило не активировалось |

Для каждого прогона отдельно оцени:

- **Discovery:** клиент показал имя/описание правила.
- **Body loaded:** журнал показывает чтение/инъекцию полного тела и конкретный путь.
- **Behavior:** выполненный код возвращает ожидаемое значение.
- **Native routing:** тело загружено механизмом skills/rules клиента. Если агент сам
  нашёл `.agents/project/.../SKILL.md` обычным поиском, отметь `file-search`, а native
  routing оставь неподтверждённым. Это не доказательство работы адаптера клиента.

Фраза модели «правило прочитано» без следа загрузки — недостаточное доказательство.
Если клиент скрывает журнал, ставь bodyLoaded=null и behaviorPassed по фактическому
результату. Если маркер появился в negative, сравнение загрязнено: выясни источник
контекста и повтори всё в новых проектах/сессиях с новым маркером.

## 4. Проверка обновления

Сначала сохрани результат `explicit` в evidence. Затем в его PowerShell-терминале
обнови только исходное правило и заново экспортируй. Команды не удаляют проект.

```powershell
$source = '.agents/project/skills/ctx-live-probe/SKILL.md'
$utf8 = New-Object System.Text.UTF8Encoding($false)
$oldBody = [IO.File]::ReadAllText((Join-Path (Get-Location) $source))
$newMarker = 'ctx-' + [guid]::NewGuid().ToString('N').Substring(0,16)
$newBody = $oldBody -replace 'ctx-[a-f0-9]{16}', $newMarker
[IO.File]::WriteAllText((Join-Path (Get-Location) $source), $newBody, $utf8)
node .agents/ctx.js export gemini
if ($LASTEXITCODE -ne 0) { throw 'Gemini export failed' }
node .agents/ctx.js export cursor
if ($LASTEXITCODE -ne 0) { throw 'Cursor export failed' }
[IO.File]::WriteAllText((Join-Path (Get-Location) 'src/status.cjs'), "exports.getStatus = () => ({ ok: false });`n", $utf8)
Get-FileHash -Algorithm SHA256 $source
$newMarker
```

Сохрани новый маркер и хеш вне проекта, в evidence. Создай новый чат в `explicit`
и повтори явный запрос. Результат должен содержать новое значение source.
Если требуется reload/restart, запиши это. Старый маркер означает возможный кеш
или загрузку другого файла; это полезная находка, а не повод скрыть попытку.

## 5. Что передать для разбора

Передай папку evidence, заполненный results-template.json, transcript каждого
условия и получившиеся status.cjs/sum.cjs, разложенные по клиенту и условию.
Укажи команды проверки с выходными значениями, ошибки, число повторов и время
настройки. Никакие API-ключи, .env, cookie или auth-файлы не нужны.
Скриншоты нужны только там, где список правил или событие активации нельзя
экспортировать текстом. Отсутствующие данные помечай null/«не видно».

Минимальный достаточный результат: discovery + явное применение + чистый
отрицательный контроль. Автоматический выбор, ненужная активация и обновление
оцениваются отдельно. Один успех не устанавливает надёжность; если есть сбои,
повтори три раза в свежих наборах и покажи все попытки с общим знаменателем.

После этого возьми одну обычную задачу из своего проекта и одно реальное правило
команды. Запиши трудность настройки, нарушенные правила и время ручных исправлений.
Для оценки пользы сравни с ручным подключением того же правила. Контрольный маркер
сам по себе не доказывает экономию токенов или улучшение качества разработки.
