# Сценарий README demo: ContextOS

Статус: сценарий для будущей записи. Запуски сравнения и результаты для этого
сценария ещё не получены. Подготовка demo-проекта, проверок и медиа — отдельная
работа. Этот документ не запускает модель и не меняет публичный README.

## Формат

- Полное видео: примерно 3 минуты 45 секунд.
- GIF для верхней части README: 25–30 секунд, без звука.
- Запись: 1920×1080, крупный шрифт терминала и редактора.
- Русская озвучка; для публичного GitHub — английские субтитры.
- Показанный клиент: Codex. Точную версию клиента, модель, reasoning и версию
  ContextOS записать перед съёмкой. Не подставлять названия будущих моделей.
- Заголовок: «ContextOS: от правила команды до кода агента».
- Английский заголовок: «ContextOS: From team rules to agent changes».

Главная мысль: инженерные правила можно хранить в Git, выбирать для задачи,
экспортировать в конфигурацию клиента и проверять на рассинхронизацию.
Поведение агента показываем отдельно, по фактическим результатам.

## Подготовить до записи

1. Маленький TypeScript-проект с `src/order.ts`, функцией `createOrder` и
   работающей командой `npm test`. За основу взять существующий
   `examples/quickstart/src/order.ts`. Подготовить зависимости заранее.
2. Для новой задачи расширить правило `team-order`: имя товара обрезается по
   краям, последовательности обычных пробелов внутри заменяются одним пробелом,
   регистр сохраняется. Не заявлять, что это уже часть текущего quickstart.
3. Подготовить одинаковый стартовый код, обычные тесты и текст задания для всех
   условий. Специфическое правило нормализации не должно уже быть реализовано,
   раскрыто комментарием в коде или подсказано видимыми тестами.
4. Подготовить независимые проверки до запусков. Сохранить их вне доступных
   агентам папок. Проверять ими копию результата после окончания каждого запуска.
5. Создать три отдельных проекта A/B/C из одного исходного состояния. Открывать
   клиент только в конкретном проекте, не в общем родительском каталоге.
6. Проверить, что A/B не наследуют ContextOS или team-order из родительских
   папок, глобальных skills, памяти либо истории. Общие настройки клиента
   должны совпадать. Если изоляция не подтверждена, не называть A контролем без
   ContextOS.
7. В B поместить те же требования дословно в нативный файл инструкций клиента
   (`AGENTS.md` для Codex). В C хранить их как проектный skill ContextOS.
8. Зафиксировать версии, исходную ревизию, модель, reasoning, общий лимит времени
   и доступные инструменты. Для каждого запуска использовать свежую сессию.
9. Для demo сделать три повторения на условие: девять запусков одной задачи.
   Заранее выбрать правило отбора видеозаписи: показать первый завершённый
   запуск каждого условия. В таблице учесть все девять, включая ошибки и таймауты.
10. Оценивать первую завершённую попытку без ручных подсказок и исправлений.
    Если нужен дополнительный одинаковый этап исправления, оценивать его отдельно.
11. Ускорять ожидание в монтаже с видимой пометкой `Sped up`. Сохранять полные
    записи и вывод проверок. Принимать или публиковать выводы только после
    фактических запусков.

Одна задача с повторениями показывает конкретный сценарий; это не широкий
benchmark качества моделей. A против B показывает эффект дополнительных правил.
B против C показывает способ доставки и сопровождения этих правил.

В C установка также добавляет core и TypeScript guidance. Для сравнения именно
способа доставки предоставить B те же дополнительные документы вручную через
нативный индекс инструкций клиента и записать доступные/фактически прочитанные
документы в отчёт. Если этого не сделано, B/C сравнивают две конфигурации целиком;
разницу качества нельзя приписывать только resolver или упаковке team-order.

## Три условия

| Метка на экране | Конфигурация |
| --- | --- |
| A — No project rules | Агент без дополнительного team-order и ContextOS |
| B — Manual rules | Тот же текст требований в AGENTS.md, без ContextOS |
| C — ContextOS | Тот же текст требований в проектном skill, экспортированном ContextOS |

Одинаковый запрос во всех трёх условиях:

> Улучши нормализацию названия товара в createOrder в src/order.ts. Сохрани
> публичный API, добавь проверки и запусти тесты. Не устанавливай новые зависимости.

Не добавлять `$team-order` только в запрос C и затем объявлять результат
сравнением автоматической загрузки. Явная активация — отдельный сценарий.

## Сцена 7 — проверка результата, 02:40–03:00

**Экран:** независимые проверки каждого diff и таблица всех повторений.
Числа подставить только из сохранённых результатов:

| Check | A | B | C |
| --- | --- | --- | --- |
| Existing behavior preserved | [result] | [result] | [result] |
| Team normalization rules | [result] | [result] | [result] |
| Agent added useful tests | [result] | [result] | [result] |
| Instruction loading observed | [status] | [status] | [status] |

Загрузка не считается критерием для A: поставить `N/A`. Для B/C статус получать
из событий клиента. Независимые проверки поведения и проверку тестов агента
оценивать отдельно. Таймауты и технические ошибки показывать явно.

**Озвучка:**

> Проверяем готовый код, а не уверенность ответа. Сохранился ли API?
> Выполняется ли правило нормализации? Есть ли полезные тесты? В таблице
> результаты всех повторений этого сценария.

**Выбрать одну реплику по фактическому исходу:**

- Если B/C соблюдают правило чаще A:
  > В этом сценарии дополнительные правила помогли соблюсти соглашение.
  > Это показывает эффект контекста. Отличие ContextOS от ручного варианта
  > посмотрим на обновлении правил.
- Если все справились:
  > На этой задаче все варианты справились. Преимущества по качеству здесь
  > не обнаружено. Дальше покажу сопровождение правил через ContextOS.
- Если C не загрузил skill или нарушил правило:
  > В этом запуске ContextOS [не подтвердил загрузку / не привёл к соблюдению
  > правила]. Результат сохранён в сравнении. Экспорт и поведение клиента
  > проверяются отдельно.

Не произносить «ИИ стал умнее», «всегда соблюдает правила» или «экономит X%»,
если эти выводы не установлены подходящим отдельным измерением.

## Приложение: текст предлагаемого проектного skill

Исходник `.agents/project/skills/team-order/SKILL.md`:

```markdown
---
name: team-order
description: Team conventions for changes to createOrder and item name normalization in src/order.ts.
---
# Team order conventions

- Keep createOrder pure: no network or database calls.
- Preserve the public { item, quantity } result shape.
- Trim ordinary spaces at both ends of item names.
- Replace runs of ordinary spaces inside item names with one space.
- Preserve item name letter case.
- Reject empty item names and quantities that are not positive integers.
- Check valid and invalid inputs before reporting completion.

These instructions guide an agent; application validation is implemented and tested separately.
```

Исходник `.agents/project/skills/team-order/skill.yaml`:

```yaml
schemaVersion: 2
name: team-order
type: instruction-only
description: Team conventions for changes to createOrder and item name normalization in src/order.ts.
resources:
  - SKILL.md
```

В ручном условии B использовать тот же текст требований из тела SKILL.md;
frontmatter и manifest нужны для упаковки C, их не считать требованиями поведения.

## Приложение: независимые проверки результата

Подготовить до запуска агентов; здесь перечислены критерии, а не готовый test runner.

- `createOrder("Tea", 2)` возвращает `{ item: "Tea", quantity: 2 }`.
- `createOrder("  Green   Tea  ", 2)` возвращает имя `Green Tea`.
- `createOrder("  gReEn   Tea  ", 2)` сохраняет регистр: `gReEn Tea`.
- Пустое или состоящее из пробелов имя отвергается.
- `0`, отрицательное и дробное количество отвергаются.
- Публичный результат содержит только item и quantity.
- В функции не добавлены сеть, БД или новые зависимости; проверить diff отдельно.
- Добавленные агентом тесты исполняются и проверяют поведение; оценить отдельно
  от результатов независимых проверок.

Для записей сохранять исходную ревизию, diff, client/model settings, события
чтения инструкций, команды проверок и их exit codes. В публичную копию выносить
только специально подготовленную демонстрацию с несекретными данными.
